# Patrones y evidencia

Rutas relativas a la raíz. En Payments, el prefijo abreviado `P/` significa `backend/apps/payments-service/src/`.

| Patrón               | Problema / archivos                                                                                                  | Flujo y evidencia                                                                                           | Trade-off / Clean Architecture                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Microservices        | Aislar pagos: `backend/apps/api-gateway/src/main.ts`, `P/main.ts`                                                    | Dos procesos, healthchecks; `backend/test/e2e/http.test.ts` cruza HTTP real                                 | Más procesos, contratos y observabilidad; aplicación independiente de transporte                 |
| API Gateway          | Un punto de entrada: `backend/apps/api-gateway/src/main.ts`                                                          | Frontend → Gateway → Payments; propaga requestId, timeout y error 503; e2e                                  | Agrega salto y posible cuello de botella; no decide pagos                                        |
| Database per Service | Evitar acoplamiento por tablas: `P/infrastructure/database/prisma.repositories.ts`, `backend/prisma/schema.prisma`   | Solo Payments importa Prisma; evidencia persistida en e2e                                                   | Dificulta transacciones distribuidas; saleId/merchantId son referencias simples                  |
| Strategy             | Sustituir política: `P/application/ports/ports.ts`, `P/application/tron-usdt-verification.strategy.ts`               | VerifyPayment → estrategia; prueba «Strategy sustituible»                                                   | Interfaces adicionales; caso de uso depende del puerto                                           |
| Proxy                | Resiliencia: `P/infrastructure/blockchain/provider.proxy.ts`                                                         | Timeout, retry limitado y traducción; pruebas de timeout y número de intentos                               | Retries añaden latencia; errores de negocio definitivos no se reintentan                         |
| Singleton DI         | Reutilizar recursos: `P/presentation/routes-or-modules/payments.module.ts`, `P/infrastructure/config/config.ts`      | Factory providers de alcance predeterminado; e2e compara identidad de AppConfig, Proxy y PaymentsHttpClient | Estado mutable compartido sería difícil de probar; configuración inmutable y composición externa |
| Repository / DIP     | Independizar casos de uso de SQL: `P/application/ports/ports.ts`, `P/infrastructure/database/prisma.repositories.ts` | Tests usan `backend/test/support/memory.ts`; e2e usa Prisma real                                            | Más abstracciones; infraestructura implementa puertos de aplicación                              |

El cliente Prisma compartido pertenece al repositorio singleton y se desconecta al cerrar Nest. El cliente HTTP del Gateway es un provider singleton; usa `fetch` y su pool de conexiones del proceso. El AsyncLocalStorage en `backend/libs/contracts/http.ts` lleva contexto de petición sin un objeto global mutable por solicitud.

El proveedor operativo es exclusivamente `SimulatedBlockchainProvider`, construido en PaymentsModule y envuelto por el Proxy. No existe un TronGridClient implementado; las variables TRONGRID son una reserva para una extensión pendiente.
